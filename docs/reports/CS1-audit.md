## B. "Tier passed" / "RS Leader" mapping (Today Move form)
- **RS Leader → `eval.rs.sustained = passed`** (as instructed). In the form it becomes the RS block of the Evaluation sheet.
- **"Tier passed"** meant: the Candidate passed the quick Tier screen (A-Fortress, A-Growth or B per TQ1 criteria) — i.e. a *Tier* verdict, whose definitions (ROIC/ND/FCF vs revenue growth) are **not** the same as the new Fortress / Proven / Emerging definitions. **Proposed mapping: none (no auto-mapping).** Removed as a checkbox; the user sets Fortress / Proven / Emerging explicitly (default `untested`, never assumed pass). Legacy `tier` stays visible as history. Why: any mapping (A-F→Fortress, A-G→Emerging…) would be a guess and a hidden Tier→eval→★ path.
- Old Watchlist docs with `promoted_by:['rs']` are **not** auto-converted to `rs.sustained = passed` (that would assume a pass). They show as "Needs evaluation" until edited; existing Watchlist items are never deleted/moved (Pending Review marker only).

## C. New data (all additive)
- `stockNotes/{wlSymKey}.eval = {fortress, proven, emerging, rs:{sustained,b26,b52}, gate5:[q1,q2,q3], stars:0–3, stars_src:'manual', date}` — key = `snKey(sym)` = ticker (+market via the `.BK` rule) — one record per ticker+market, shared by Candidate and Watchlist forms, kept when a Candidate moves to the Watchlist and across reloads. Status values `untested|passed|failed|insufficient|na`; Gate 5 item: `passed` = answered **No** (no red flag), `failed` = answered **Yes**. Default `untested`.
- ★ is manual now (`stars_src:'manual'`). `Calc.starsFromEval(eval)` implements the Part A table top-to-bottom (pure, tested) but is **not** used to set ★; when ≠ manual ★, a muted hint `Eval suggests ★★` is shown. Existing Watchlist `stars` (TD4a) are read as fallback (and mirrored when ★ is set on a Watchlist item) so nothing already rated is lost; the eval record wins when it exists.
- Plan/card snapshot `cs = {eval, date, stars, stars_src, baseRiskPct, riskAmt, adj:{ff, dd}, equity, used, budget, capKey}` written at save; later eval/★ edits never touch saved plans/positions.
- Needs Firestore rules? `stockNotes` already has a rule (VW1); `eval` is a field inside the same documents → **no new rule**.
