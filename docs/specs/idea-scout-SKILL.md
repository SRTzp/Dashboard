# Idea Scout

## เป้าหมาย
หน้าที่ = **จัดระเบียบไอเดีย → หาว่าใครได้/เสียประโยชน์ → เลือกบริษัทที่ควรใช้เวลาศึกษาต่อ** · ไม่ใช่วิเคราะห์บริษัท (นั่นคืองานของ `living-thesis`)
งานเสร็จเมื่อ: อธิบายได้ว่า **"เลือกบริษัทนี้เพราะอะไร และต้องพิสูจน์อะไร"** แม้สุดท้าย Living Thesis จะพบว่าบริษัทไม่น่าสนใจก็ตาม
ผลลัพธ์ = JSON ไฟล์เดียว (`idea@1` หรือ `idea-match@1`) → ผู้ใช้ 📥 Import ในแอป
ใช้กับ **หุ้น Core เท่านั้น** (Sat = futures ไม่ใช้ skill นี้)

**ลำดับความสำคัญ: ถูกต้อง > ครบ > ประหยัด token**

## โหมด

| โหมด | ใช้เมื่อ | ทำอะไร | ต้องมี | งบ token |
|---|---|---|---|---|
| `scan` (default) | ไอเดียใหม่ | ส่วน 1–4: ไอเดีย · กลไก · หลักฐาน · Value chain + ฝั่งเสีย + asset อื่น + วันนัดตรวจ · **ไม่ค้นหาบริษัท** | ไอเดีย 1–2 ประโยค (+ โน้ตผู้ใช้ถ้ามี) | ≤40k |
| `pick` | ผู้ใช้เลือกส่วน value chain แล้ว | ส่วน 5–6: บริษัทในส่วนที่เลือก + แหล่งยืนยัน + ลำดับศึกษา · ตรวจบริษัทสถานะ "รอตรวจ" จาก match | JSON เดิม + ส่วนที่เลือก (หรือ `pick: true` ใน JSON) | ≤40k |
| `full` | ผู้ใช้มั่นใจธีมแล้ว / บอกส่วนที่จะดูมาตั้งแต่แรก | scan + pick รอบเดียว | ไอเดีย + ส่วนที่จะดู | ≤70k |
| `match` | มี list หุ้นจาก screener | จับคู่หุ้นกับไอเดียที่มีอยู่ จากชื่อ + Industry · **ไม่ค้นเว็บ** | list ticker (+ Industry) + "สรุปไอเดียสำหรับจับคู่" จากแอป | ~3–5k / 50 ตัว |
| `update` | ถึงวันนัดตรวจ / ข่าวชนสัญญาณพัก / ผู้ใช้ตอบข้อที่ขาด | เช็คสัญญาณพัก + หลักฐานใหม่หลังวันที่เดิม + ตั้งวันนัดใหม่ · หรือรับสิ่งที่ผู้ใช้หามาแล้วปิดข้อที่ขาด | JSON เดิม (+ คำตอบผู้ใช้) | ≤20k · ตอบข้อที่ขาด ≈ 5–15k |

ผู้ใช้ไม่ระบุโหมด: ไม่มี JSON → `scan` · มี JSON ที่ยังไม่มีบริษัท + บอกส่วน → `pick` · มี JSON ที่มีบริษัทแล้ว → `update` · มี list หุ้น → `match`
ทำ **ทีละ 1 ไอเดีย** (ยกเว้น `match` ที่จับคู่กับหลายไอเดียพร้อมกัน)

## Pre-flight (ถามเฉพาะที่ไม่ชัด · ไม่เกิน 1 คำถาม)
- ตลาด: US / TH / ทั้งคู่ — ไม่บอก = US
- `pick` ไม่มี JSON เดิม → ขอ (แอป: การ์ดไอเดีย ⋯ → Export JSON) · ไม่มีส่วนที่เลือก → ถามว่าจะดูส่วนไหน (เสนอส่วนที่ scan แนะนำไว้)
- `match` ไม่มี "สรุปไอเดียสำหรับจับคู่" → ขอ (แอป: Candidates → 📋 จับคู่ list → คัดลอกคำสั่ง match)

## ไอเดียของผู้ใช้เอง
ผู้ใช้อาจแปะโน้ต: ไอเดีย · กลไกที่คิด · หุ้นที่นึกไว้ · ส่วนที่ไม่แน่ใจ (กรอกไม่ครบได้)
1. เก็บข้อความผู้ใช้ไว้ใน `user_notes` **ตามที่เขียนมา** (ห้ามเกลา) · หลักฐานที่มาจากโน้ตผู้ใช้ติดป้าย `U`
2. ถือเป็น **สมมติฐานที่ต้องตรวจ** ไม่ใช่คำตอบ · ช่องที่ผู้ใช้เว้นไว้ AI เติมเอง
3. หลักฐานขัดกับที่ผู้ใช้คิด → เขียนใน `user_notes_check` ว่า "ขัดตรงไหน เพราะอะไร" · **ห้ามเขียนทับความคิดผู้ใช้** · ผู้ใช้ตัดสินเอง
4. หุ้นที่ผู้ใช้นึกไว้ → ใส่ `candidates[]` (pick/full) แต่ต้องมี `relevance_src` เหมือนตัวอื่น · หาไม่เจอ = `state: "wait"` + บอกเหตุผล · ตัวที่ AI เห็นว่าตรงกว่า → ใส่แยก `from: "ai"`
5. ไอเดียที่แอปสร้างจาก "กลุ่มที่วิ่งแต่ยังไม่มีไอเดีย" (`origin` = TradingView screen) → โจทย์หลักของ scan = **กลุ่มนี้วิ่งเพราะอะไร** · แยกให้ชัดว่าเป็นแนวโน้มระยะยาว / วัฏจักร / เหตุการณ์ชั่วคราว (ข่าวครั้งเดียว · short squeeze · กระแสระยะสั้น) · ราคาขึ้นอย่างเดียวไม่ใช่หลักฐานของธีม
6. **บังคับหลักฐานขัดแย้ง ≥1 เสมอ** — ไอเดียของตัวเองเสี่ยง confirmation bias (เห็นแต่สิ่งที่ยืนยันความคิดเดิม)

## ป้ายกำกับหลักฐาน (`evidence[].tag` · ชุดเดียวกับ living-thesis + U)
| ป้าย | ใช้เมื่อ |
|---|---|
| `F` | ข้อเท็จจริงจากเอกสารบริษัท / หน่วยงานทางการ — ต้องมีแหล่ง + วันที่ |
| `C` | คำนวณเอง — บอกสูตร |
| `M` | Guidance / คำพูดผู้บริหาร — ยังไม่ใช่ผลจริง |
| `I` | ตีความจากหลักฐาน |
| `A` | สมมติฐานอนาคต |
| `U` | ผู้ใช้บอกมา — ยังไม่ได้ตรวจ |

ในเนื้อหา (ข้อความที่แสดงในการ์ด) ใช้วงเล็บคำเต็มแทนป้ายย่อ: `(Mgmt)` `(Inference)` `(Assumption)` `(Unknown — หาไม่เจอ)` · ข้อเท็จจริงไม่ต้องใส่วงเล็บ (แหล่งอยู่ใน `evidence[]`)
**แยก "ผลจริง / คำคาดการณ์ / การตีความ" เสมอ** — ห้ามเขียนด้วยน้ำเสียงเดียวกัน

## วิธีเขียน (บังคับ)
ผู้อ่าน = นักลงทุนที่ไม่ใช่ผู้เชี่ยวชาญอุตสาหกรรมนั้น · **ยาวขึ้นได้ถ้าทำให้เข้าใจ** · แต่ทุกช่องใน JSON สั้นที่สุดเท่าที่ยังเข้าใจ (การ์ดต้องไม่รก)
1. ศัพท์เฉพาะ: คง keyword อังกฤษครอบ `[[ ]]` + ใส่ความหมายใน `terms[]` (แอปแตะดูได้) · ไม่ต้องอธิบายในวงเล็บซ้ำ
   - ไม่ต้องครอบ: moat · switching cost · margin · FCF · capex · guidance · hyperscaler · value chain · bottleneck · YoY · TTM
2. ประโยคเต็ม ภาษาไทยง่าย ๆ · 1 ช่อง = 1 เรื่อง
3. ตัวเลขมีตัวเทียบ + ทิศ: ❌ `capex 100B` → ✅ `capex ปีหน้าเพิ่มจาก X เป็น Y (+Z%)`
4. ห้ามข้อความลอย ๆ แบบ "ตลาดใหญ่ / megatrend / ได้ประโยชน์จาก AI" — ต้องบอก **ใครจ่าย จ่ายเพื่ออะไร ผ่านตัวเลขไหน**
5. ห้ามใส่ป้าย `[F]` `[M]` ฯลฯ ในเนื้อหา

## กฎเหล็ก
1. **ไม่มีหลักฐาน = Unknown** ห้ามเติมจากความจำ ห้ามแต่งตัวเลข / ลิงก์ / วันที่
2. **ตัวเลขบริษัทจากเอกสารบริษัทเท่านั้น** (8-K / 10-Q / 10-K / 56-1 / IR) · ข่าว/บทความใช้กับเนื้อความเชิงคุณภาพ · หลายบทความลอกข่าวเดียวกัน = 1 แหล่ง
3. **ธีมถูก ≠ บริษัทได้ประโยชน์** — ทุกบริษัทต้องตอบ "นัยต่อทั้งบริษัท" (สัดส่วนรายได้ที่เกี่ยว · ไม่รู้ = Unknown) และ "ไม่ได้ประโยชน์แม้ไอเดียถูก ถ้า…"
4. **รายได้เพิ่ม ≠ กำไรเพิ่ม** — ทุกส่วนของ value chain ต้องมี `trap` (อะไรทำให้รายได้เพิ่มแต่กำไรไม่เพิ่ม: ราคาถูกคุม · ลูกค้ากระจุก · supply ขยายทัน · ต้นทุนวัตถุดิบขึ้น ฯลฯ)
5. **หลักฐานขัดแย้ง ≥1 · สัญญาณพัก ≥1** ทุกไอเดีย · หาไม่เจอจริง → เขียนใน `gaps[]` ว่าหาแล้วไม่เจอ (ห้ามแต่งให้ครบ)
6. **AI ไม่ตัดสินแทนผู้ใช้** — `status` เสนอได้แค่ `exploring` / `need_evidence` / `ready` / `parked` · `rank` / `state` เป็นข้อเสนอ · ผู้ใช้แก้ในแอป · ห้ามบอกซื้อ/ขาย/ราคาเป้าหมาย
7. **`ready` ได้เมื่อครบ 4 ข้อเท่านั้น:** หลักฐาน `against` ≥1 · `kill` ≥1 · บริษัท `state: "study"` ที่มี `relevance_src` ≥1 · ไม่มี `gaps[]` ระดับ `must` ที่ `status: "open"` (แอปบังคับซ้ำ)
8. **`losers[]` / `candidates[]` ต้องมี ticker จริง + เหตุผล + แหล่ง** · ticker ไม่แน่ใจ (ชื่อซ้ำ / หลายตลาด) → ตรวจก่อน ห้ามเดา
9. **`segments[]` ของบริษัท ใช้ชื่อตาม `chain.segments[].name` ของไอเดียนั้นเท่านั้น** · ส่วนหลักขึ้นก่อน · บริษัทหลายธุรกิจอยู่ได้หลายส่วน
10. **`assets[]` (XAU · BTC · Brent · S50) = ข้อมูลประกอบ ไม่ใช่สัญญาณเทรด** · ใส่เฉพาะเมื่อกลไกชัด · สูงสุด 3 · ป้าย `I` เสมอ · ไม่ชัด = ไม่ใส่
11. **สอง AI เห็นตรงกัน ≠ ยืนยัน** — กลับไปที่ต้นทางเสมอ

## การดึงข้อมูล

| โหมด | แหล่ง | งบ search / fetch |
|---|---|---|
| `scan` | ข่าว/บทความที่มีวันที่ · รายงานหน่วยงาน/สมาคมอุตสาหกรรม · transcript ของผู้จ่ายเงินรายใหญ่ (เช่น ลูกค้าปลายทาง) · ข้อมูลอุปทาน/คอขวด | search 5–6 · fetch 3–4 |
| `pick` | 10-K Item 1 (ธุรกิจ + segment) · 8-K 2.02 EX-99.1 (segment revenue) · IR presentation · TH: 56-1 / IR | ต่อบริษัท: search 1 · fetch 1–2 |
| `match` | **ไม่ค้นเว็บ** — ใช้ชื่อ + Industry + สรุปไอเดียที่ผู้ใช้ส่งมาเท่านั้น | 0 |
| `update` | เฉพาะเอกสาร/ข่าวหลัง `date` เดิม | search 1–2 · fetch 1–2 |

US filings: ใช้วิธีเดียวกับ living-thesis — EDGAR full-text search (`efts.sec.gov/LATEST/search-index`) หาไฟล์ · ชื่อไฟล์อ่านจาก `_id` ห้ามเดา · ห้ามดึง `companyfacts` · ห้าม DEF 14A ผ่าน WebFetch
Date-anchor query เสมอ (ใส่เดือน/ปี) · ticker สั้นให้ค้นคู่ชื่อบริษัท (กันได้หุ้นผิดตัว)
ผล search **พลิก** ข้อสรุป → เปิดต้นทางยืนยันเฉพาะจุดนั้น

## Workflow — `scan`
1. **ไอเดีย:** อะไรเปลี่ยน · ตัวผลักดัน · ทำไมตอนนี้ · ประเภท (`structural` / `cyclical` / `event`) + เหตุผล · รู้แล้ว vs ยังเป็นสมมติฐาน
   - ประโยคเดียว `one_liner` = 4 ช่อง: เมื่อ **[ก]** เปลี่ยน → **[ผู้จ่าย]** ต้องจ่าย/ใช้กับ **[ค]** มากขึ้น/น้อยลง → เพราะ **[ง]**
2. **กลไก:** เส้นเหตุ-ผล 4–6 ขั้น (การเปลี่ยนแปลง → ผู้จ่ายต้องทำอะไร → ความต้องการเปลี่ยน → ธุรกิจแบบไหนได้ → ผ่านยอดขาย/ราคา/ต้นทุน/ปริมาณ) · ระบุขั้น `weak: true` 1 ขั้น = จุดที่ไม่แน่นอนที่สุด · ใครจ่ายจริง · ทำไมต้องจ่าย · ทางเลือกอื่น (เลื่อน / ทำเอง / ของทดแทน)
3. **หลักฐาน:** 3–6 แถว (สนับสนุน + ขัดแย้ง ≥1) · สัญญาณพัก 2–3 ตัว **วัดได้** + ค่าตอนนี้ + `level` · ข้อมูลที่ขาด + หาจากไหน + ระดับ (`must` / `track` / `skip` — `must` = ไม่รู้แล้วตัดสินไม่ได้ · ใช้ให้น้อย 1–3 ข้อ) · คำอธิบายทางเลือก (ถ้ามีเหตุผลอื่นที่อธิบายสิ่งที่เห็นได้)
4. **Value chain:** 3–6 ส่วน ต้นน้ำ → ปลายน้ำ · แต่ละส่วน: บทบาท · `effect` ได้/เสีย/ปนกัน · `trap` · `industries[]` (ชื่อตามคอลัมน์ Industry ของ TradingView 1–4 ชื่อ — ไม่แน่ใจชื่อ ให้ใส่หลายตัวเลือก แอปจับคู่ไม่สนตัวพิมพ์) · Bottleneck · ส่วนที่ **เสนอให้ดูก่อน** (`suggest: true` 1–2 ส่วน + เหตุผลใน `suggest_why`) · ส่วนที่ไม่เสนอ + เหตุผล (`skipped`)
   - **ห้ามตั้ง `pick: true`** — ผู้ใช้เลือกเอง
5. **ฝั่งเสีย:** `losers[]` 0–5 ตัว (ticker + เหตุผล + แหล่ง) · ไม่มีหลักฐานพอ = ไม่ใส่
6. **asset อื่น:** `assets[]` 0–3 (กฎข้อ 10)
7. **สถานะ + วันนัด:** เสนอ `status` · ถ้า `need_evidence` → `recheck` = วันที่ที่หลักฐานจะออก (เช่น วันประกาศงบ / ตัวเลขทางการ) + รออะไร · ไม่รู้วัน → +30 วัน
8. `call`: `more_evidence` / `park` / `handoff` (scan ยังไม่มีบริษัท → ใช้ `more_evidence` หรือ "เลือกส่วนแล้วรัน pick")

## Workflow — `pick`
1. อ่าน JSON เดิม · ส่วนที่ศึกษา = ที่ผู้ใช้บอก หรือ `chain.segments[].pick === true`
2. ต่อส่วน: หาบริษัทจดทะเบียน 2–5 ตัว (ตลาดตาม `scope`) · ใส่ตัวที่อยู่ใน `user_notes.tickers` ก่อน (ถ้าอยู่ในส่วนนั้น) · ตรวจ `state: "screen"` ที่มาจาก match ด้วย
3. ต่อบริษัท (เปิด 10-K Item 1 / segment table):
   - `product` ธุรกิจที่เกี่ยว · `mechanism` ได้ประโยชน์ผ่านอะไร · `segments[]`
   - `exposure` นัยต่อทั้งบริษัท (สัดส่วนรายได้ + งวด · ไม่เปิดเผย = Unknown)
   - `relevance_src` แหล่งที่ยืนยันว่าบริษัททำธุรกิจนี้จริง (เอกสารบริษัท + วันที่) · **ไม่มี = ห้าม `state: "study"`**
   - `why_this` ทำไมตัวนี้ (เทียบกับตัวอื่นในรายการ) · `fail_even_if_right` · `questions[]` 2–3 ข้อให้ Living Thesis ตรวจ
   - เสนอ `rank` (1 = ทำการบ้านก่อน) + `state` (`study` / `wait` / `park`) + `state_why`
4. หลักฐานใหม่ระหว่างทาง → เติม `evidence[]` / แก้ส่วน 1–4 เฉพาะจุดที่เปลี่ยน · ห้ามเขียนใหม่ทั้งฉบับ
5. เติม `log[]` 1 บรรทัด

## Workflow — `full`
`scan` ข้อ 1–8 (ย่อ: หลักฐาน 3–4 แถว) → ตั้ง `pick: true` ให้ส่วนที่ผู้ใช้บอก → `pick` ข้อ 2–5

## Workflow — `match`
อินพุต: list ticker (+ Description + Industry) + "สรุปไอเดียสำหรับจับคู่" (ต่อไอเดีย: id · ประโยคเดียว · segments ได้/เสีย · industries)
1. ต่อหุ้น: ดูชื่อ + Industry → `likely` / `unsure` / ไม่เกี่ยว · ไอเดียไหน · `side` ได้/เสีย · `segments[]` (ชื่อตามไอเดีย) · `why` 1 บรรทัด
2. ใช้ความรู้ทั่วไปได้ **เฉพาะคัดคร่าว ๆ** · ป้าย `I` เสมอ · ไม่รู้จักบริษัท / ไม่แน่ใจ = `unsure` (ห้ามเดาเพื่อให้ได้คำตอบ)
3. ไม่เกี่ยว → ไม่ต้องส่ง · นับใน `dropped`
4. ห้ามค้นเว็บ · ห้ามใส่ตัวเลข
5. ส่ง `idea-match@1` → แอปใส่ผลเป็น `state: "screen"` (รอตรวจ) · ผู้ใช้ค่อยรัน `pick` กับตัวที่อยากไปต่อ

## Workflow — `update`
1. อ่าน JSON เดิม → ค้นเฉพาะสิ่งที่ออกหลัง `date` เดิม / ตามที่ `recheck.what` รอ
2. ไล่ `kill[]` ทุกตัว: อัปเดต `now` + `level` (`hit` → เสนอ `status: "parked"` ใน `call` · **ไม่เปลี่ยน status เอง**)
3. เติม `evidence[]` แถวใหม่ (ห้ามลบแถวเดิม · ข้อมูลขัดของเดิม → แก้แถวนั้น + บันทึกใน log)
4. ปิด `gaps[]` ที่ตอบได้ · ตั้ง `recheck` ใหม่
5. เติม `log[]` 1 บรรทัด: อะไรเปลี่ยน · สัญญาณไหนขยับ · ข้อเสนอสถานะ

## Workflow — `update` · ตอบข้อที่ขาด (ผู้ใช้หามาเอง)
อินพุต: `ตอบข้อที่ขาด #id` + สิ่งที่ผู้ใช้ส่ง (ข้อความ / ลิงก์ / ภาพ / PDF) + JSON เดิม
1. **อ่านเฉพาะสิ่งที่ผู้ใช้ส่ง** ไม่ค้นเว็บเพิ่ม · ยกเว้น: ลิงก์ที่ผู้ใช้ให้ → เปิดได้ · ตัวเลขบริษัทจากข่าว/โบรก → เปิดเอกสารบริษัทยืนยันเฉพาะจุดนั้น (≤1–2 fetch)
2. ป้าย: เอกสารบริษัท = `F` · ความเห็นโบรก/บทความ = `I` · ความจำ/สิ่งที่ผู้ใช้สังเกต = `U` · ยืนยันไม่ได้ = บอกตรง ๆ
3. ตอบได้ → `status: "answered"` + `answer` (สั้น · บอกว่าตอบคำถามอย่างไร) + `answer_src` + `answered_at` · เติม `evidence[]` แถวใหม่
4. ตอบได้บางส่วน → คง `open` + เขียนใน `answer` ว่าได้อะไรแล้ว ยังขาดอะไร
5. ผู้ใช้บอกว่าหาไม่ได้ / บริษัทไม่เปิดเผย → `unanswerable` + เหตุผล + ใช้อะไรแทน (proxy · ประกาศข้อจำกัด) หรือ "ยอมรับความเสี่ยง"
6. ขัดกับหลักฐานเดิม → **ไม่ทับ** · เก็บทั้งสองแถว + เขียนใน log ว่าต่างตรงไหน
7. **ผลต่อไอเดีย:** ไล่ดูว่าคำตอบเปลี่ยน `kill` / `mechanism.weakest` / `candidates[].state` / `status` ไหม → เปลี่ยนเฉพาะที่หลักฐานบังคับ · บันทึก `log[]` 1 บรรทัด: "ตอบ #id → เปลี่ยนอะไร"
8. แชท: ข้อไหนปิด · เปลี่ยนอะไรในไอเดีย · ข้อ `must` ที่ยังเปิด

## Verify (บังคับก่อนส่ง)
1. JSON parse ได้ (`python3 -c "import json;json.load(open(f))"`) · ไม่มี comment / trailing comma / placeholder ค้าง
2. ทุก `evidence[]` แถว `F`/`M` มี `src` + `date` ที่เปิดอ่านจริง · ตัวเลขบริษัทที่อ้างข่าว = ผิดกฎ → แก้หรือเปลี่ยนเป็น Unknown
3. มี `against` ≥1 · `kill` ≥1 · ทุก `kill` วัดได้ + มี `now`
4. ทุกส่วน value chain มี `trap` + `industries[]`
5. ทุก `candidates[].segments` / `results[].segments` อยู่ใน `chain.segments[].name`
6. `state: "study"` ทุกตัวมี `relevance_src` · `status: "ready"` ผ่านกฎเหล็กข้อ 7 · ทุก `gaps[]` มี `id` + `priority` + `status` · `unanswerable` มีเหตุผล
7. ticker ทุกตัวตรวจแล้วว่าตรงบริษัท (กันชื่อซ้ำ)
8. ทุก `[[คำ]]` มีใน `terms[]` และทุกคำใน `terms[]` ถูกใช้จริง
9. สุ่มอ่าน 3 ช่อง: มีเหตุผลในตัว ไม่ใช่คำนามลอย ๆ · ไม่มีข้อความลอยแบบ "megatrend"
10. `audit`: จำนวน search · fetch · เดาชื่อไฟล์พลาด · token โดยประมาณ

## Deliver
เซฟ `{id}_idea.json` (หรือ `match_{YYYYMMDD}.json`) ลง outputs → บอก "📥 Import ในหน้า Watch › Ideas" (match: "Candidates › 📥")
ตอบในแชทสั้น ๆ เท่านั้น:
- **scan:** ประโยคเดียว · สถานะที่เสนอ · ส่วน value chain ที่เสนอให้ดูก่อน + เหตุผล 1 บรรทัด · จุดอ่อนสุดของไอเดีย · ถ้าผู้ใช้ส่งโน้ตมา: ตรงไหนที่หลักฐานขัดกับที่คิด
- **pick / full:** ลำดับศึกษา 1–3 + เหตุผลคนละ 1 บรรทัด · ตัวที่ยังไม่มีแหล่งยืนยัน
- **match:** จำนวน likely / unsure / dropped · 3 ตัวที่น่าไปต่อที่สุด
- **update:** อะไรเปลี่ยน · สัญญาณไหนขยับ · ข้อเสนอสถานะ
